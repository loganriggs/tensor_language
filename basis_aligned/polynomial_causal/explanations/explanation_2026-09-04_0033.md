# Below the block: where bilin18 spends its width, and a correction (2026-09-04 00:33 UTC)

Plain-language chapter (Claude lane, ledger §2759–§2776), expanding project shorthand. Sign convention throughout (§2135):
every loss number is CE ADDED ABOVE THE REAL MODEL on 64 held-out documents — LOWER IS BETTER; the real model adds 0.

## Where the last chapter left off

The previous chapter (23:25) described bilin18 as a "width program": the back half of the network (blocks 8–17) reads and
writes through ONE shared 1024-dimensional frame (a "bus"), while the front half (blocks 0–7) uses separate, rotating frames.
The whole description cost about .036 nat at width 1024, and fell off a cliff at width 768 (about .24). The open question was
what the cliff was made of.

## The program got simpler first (§2764–§2769)

A cheaper version turned out to work: instead of sixteen frames for the front half, ONE frame per early block (attention and
MLP of block l share it) plus the bus — nine frames total — with a single write rule: a block writes into the frame of whoever
reads it next (its own MLP, the next block, or the bus), and whatever does not fit is handed to the bus. That is "program
v2": nine frames, one rule, .039 nat at width 1024 and .016 at width 1088. The early "hand-off" from one frame to the next costs
almost nothing except at blocks 6 and 7, and even there it is the bus's width, not the frame change, that hurts.

## The correction (§2770 → §2771)

I had written that program v2's cost at width 768 came from the early frames being chained. The next measurement said the
opposite: each early block, narrowed alone to 768, costs .002–.006 — trivial — while the bus alone at 768 costs .164. Under the
program's rules a conclusion that flips a prior claim needs an independent physical control before it is published, so the
flip was held for one rung. The control confirmed it and sharpened it: it is not the SHARING of the bus that hurts (the late
blocks lose .137 even when each gets its own private 768-frame), it is that blocks 8–17 genuinely use more than 768 dimensions
of their input — and the loss compounds, because each late block re-reads what the previous one wrote through the same
truncated window (ten single-block losses of .006–.014 sum to less than half the joint loss). The correction is recorded in
§2771; every measured number in §2764–§2769 stands, only the attribution changed. An "asymmetric" program (narrow early
frames, wide bus) was then tried (§2772) and is worse than the uniform one everywhere — early width costs about as much per
dimension as bus width once early WRITES are confined too. Asymmetry is closed.

## Below the block: who uses the width (§2773–§2774)

This is the new grain the user asked for — smaller than an MLP block. Of the .164 the late blocks lose at width 768:

- The MLPs' READS account for .125; the attention layers' reads for .015 — eight to one. This matches the exact-rank map from
  the 12:30 chapter: attention reads through a per-head 128-dimensional bottleneck and is genuinely low-dimensional, while the
  bilinear MLPs read the full width. So the late ATTENTION program can be narrowed almost for free; the late MLP program cannot.
- Inside the MLP — which is Down[(Left·x) ⊙ (Right·x)] — the two branches read the missing directions EQUALLY (.048 each alone)
  and super-additively: removing them from both branches costs .125, more than .048 + .049. The excess, 22% of the cost, is
  the product of the two branches' tail components — a quadratic function of the low-variance directions that no linear read
  of the main directions can supply. That is a genuinely bilinear fact about where the model computes.

## What the width is for (§2775–§2776)

Two natural stories were tested. "It's a dictionary for rare tokens" — FALSE: the loss concentrates on a decile of tokens, but
those are ORDINARY, FREQUENT targets; rare targets carry less than their share. The width sharpens everyday predictions. "It's
determined by the current token" — mostly FALSE: predicting the missing directions from the current token's embedding recovers
18% of the loss (a small, real vocabulary item — and 2.5× more loss than its share of the energy, so what token signal exists
sits exactly where the MLP weights look), leaving 82% CONTEXTUAL: state that the settled region builds from context and
re-reads, becoming more contextual with depth. Running now: whether that contextual tail is written INSIDE the settled region
(as the compounding suggests) or inherited from the front half.

## Why it matters

The width cliff is now localised to one operation — the late MLPs' bilinear read of the low-variance bus directions — and
characterised: symmetric across branches, spread across blocks, aimed at frequent tokens, mostly contextual, partly (18%)
token-determined. That takes it OUT of the project's largest open gap (tail dictionaries / coverage credit) and into the
implementation account: it is a cost of the mechanism, not a missing vocabulary. Nothing here changes the strict explained
fraction (5.348% / 10.923% / 4.727 nat / 0 of 68); these are implementation descriptions, not behaviour-level circuits, and
nothing installs into the §312 frontier.
